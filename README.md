# Customs Intelligence Platform

[Open Revenue Recovery](https://lonemompati.github.io/cip-revenue-lab/)

Start with a declaration in the **Recovery register**. Open the invoice total line, compare it with the declared amount and follow the additional duty from assessment through to collection. Select a screening queue and filter by account, commodity, minimum duty gap or case stage. Cases with uncertain evidence can be referred for a document or currency check. Search and filters update the four totals. Open a **To review** case to assess or close it. Open an assessed case to record a partial or full payment. Actions apply to the current browser tab and survive a reload.

## Open data and scope

| Input | Fields used | Source |
| --- | --- | --- |
| Shipment sample | Original shipment ID, commodity and USD declared value for 6,000 distinct shipments | Ziya, [Cross-Border Trade & Customs Delay Dataset](https://www.kaggle.com/datasets/ziya07/cross-border-trade-and-customs-delay-dataset), CC0 1.0 |
| Generated invoices | Document ID, cropped final total line, a page extract with only selected non-identity fields, and the reader output for 6,000 distinct pages | Mahmoud Limam, Marwa Dhiaf and Yousri Kessentini (2023), [FATURA](https://zenodo.org/records/8261508), [Kaggle version 1](https://www.kaggle.com/datasets/mibrahimm/fatura-dataset/versions/1), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) |
| Coursework scenario | Pairing, account aliases, assumed initial payment, additional duty assessments and receipts | Generated by the preparation and ledger code in this repository |

The source datasets have no common transaction key. The original 48 pilot cases retain their original documents and simulated opening balances. The remaining 5,952 declarations each receive an unused invoice in deterministic hash order, independent of its amount. Most shipment values are larger than the FATURA invoice totals. Each source amount is preserved. Screening coverage counts all linked pages examined by the pipeline, including pages with no usable total region. This is a teaching sample, unsuitable for estimating fraud prevalence, actual debts or model accuracy.

The downloadable data is in [data/shipments.json](data/shipments.json). All monetary numbers in the JSON and ledger are integer cents. Source rows and invoice images are independent of any revenue authority. The app needs no credentials or live data connection. The public demo focuses on USD declaration evidence. The earlier executive dashboard's 8% recovery and 14% review figures belong to a separate BWP reporting scenario.

## How a declaration becomes a balance

1. During preparation the pipeline checks each linked page. Where a TOTAL annotation exists, Tesseract’s English OCR reads that region. Missing regions remain in the document-check queue. A bare dollar sign stays unconfirmed, and an explicit EUR amount requires a currency check. Both exceptions remain outside the financial calculations. The source annotation supplies the location. Both OCR amount and currency must match its label to pass the check. We publish the cropped, enlarged line so a reviewer can inspect the same evidence. This assisted demonstration does not benchmark full-page invoice detection.
2. The scenario assumes the USD invoice total and declared value are comparable for that shipment. Only verified USD totals are compared. A currency mismatch or failed read goes to **Check evidence**. A shipment without a document has no estimated gap.
3. We assume original duty was paid at an illustrative 10%. Potential extra duty is the positive difference between duty on the document value and duty on the declared value, each rounded to cents. An officer's decision creates an assessment. Closing without extra duty leaves no debt.
4. Outstanding extra duty equals the extra assessment less additional receipts. The original duty payment is shown separately. Amounts in the cards relate to the filtered rows. The opening assessments and payments are limited to the original pilot scenarios. New positive gaps start unassessed. The screening queues retain the original result after a referral, assessment or receipt; subsequent decisions are replayed from the current tab's session.

## Run and reproduce

Use Node 22.12 or later. Run `npm ci`, then `npm run dev`. Run `npm test` to check coverage, reconciliation and safeguards. Run `npm run build` to rebuild the static site into `docs/`. GitHub Pages serves that directory on the main branch. The committed source data and invoice excerpts allow anyone to run the app without downloading Kaggle again.

To recreate the snapshot, download the shipment ZIP and version 1 of FATURA from the Kaggle links above and unpack FATURA. With Python 3.10+, Pillow and the Tesseract CLI (English language data) installed:

```sh
python3 scripts/prepare.py shipments.zip /path/to/fatura_dataset
npm test
npm run build
```

The generator verifies the original shipment CSV hash, takes the first 6,000 IDs ranked by SHA-256 of `3009:<Shipment_ID>` and uses deterministic invoice selection. Tesseract versions can affect which reads pass. Only the three shipment fields and the selected invoice evidence leave the preparation step.

## Reviewing the screening batch

The four screening outcomes partition all 6,000 declarations. Click **Positive duty gap** for comparable pairs with a potential shortfall, **No positive gap** for the other comparable pairs, **Check currency** for an ambiguous dollar sign or an explicit non-USD amount, or **Check document** for a missing total region or unverified read. The queue counts describe the full screening batch. The financial cards describe only the selected register rows. An unavailable amount appears as a dash.

Open a declaration to see the original reader evidence and the reason for its queue. Referrals and payments stay in the tab's session history. The minimum duty gap filter helps an officer prioritise larger opportunities. New invoice excerpts are stored in packs of 32 under `public/evidence-batches/` and loaded when an officer opens a case.

## Invoice matching

[Open the live matching exercise](https://lonemompati.github.io/cip-revenue-lab/#invoice-matching). Seven simulated declarations run against an independent index built from the FATURA NUMBER annotations of the 6,000 published pages. Of those pages, 5,298 have an indexable printed number. The matcher trims outer spaces and ignores case. It preserves punctuation and leading zeros and requires exactly one candidate. The declaration inputs contain no target document IDs. Missing, unknown and duplicate references enter **Check reference** with no financial estimate. A unique match opens the actual public invoice extract. These exercises have their own totals and use the same assessment and payment ledger as the main register.

- **SIM-001:** USD 215.39 declared, USD 1,715.39 invoiced. At the illustrative 10% rate the gap is USD 150.00. Assess it and record a partial or full payment.
- **SIM-002:** the declaration says USD 998.22 and the invoice says EUR 998.22. The exercise supplies an illustrative rate of USD 1.20 per EUR. Confirming that rate gives USD 1,197.86 of invoice value and USD 19.97 of potential extra duty. Assessment and payment remain separate actions.
- **SIM-003:** a worked partial recovery with USD 100 assessed, USD 60 received and USD 40 outstanding.
- **SIM-004 through SIM-007:** an agreeing value, an unknown reference, two invoices with the same printed reference, and a missing reference.

The examples illustrate discrepancies and their financial consequences. Operational findings about intent require independent evidence. The reference index can be regenerated separately with `python3 scripts/invoice_references.py /path/to/fatura_dataset`; the full preparation command also rebuilds it.
